# 一天出30条口播视频：不是手速快，是把流程拆成了流水线

**棱镜 · AI数字人系列 · 第6天**

---

上周有个做知识付费的朋友找我，说他要给自己的课程做100条切片口播，问我能不能帮忙。

我问他现在怎么做的。他说：写稿、录音、丢进工具、等渲染、下载、改名、加字幕——一条要40分钟。

100条。他算了一下，光坐在电脑前点鼠标就要67个小时。

我说你这不是效率问题，是流程问题。真正拖慢你的不是渲染，是每一条都要你亲手点十几次。

今天讲的就是这个：怎么把昨天那套本地部署的开源工具，变成一条能连续吐视频的流水线。

## 核心概念：口播视频的四段流水线

先说个类比。

手工作坊做一件衣服，一个师傅从裁布到缝扣子全干完。流水线不一样——裁剪、缝合、锁边、熨烫，每站只干一件事，衣服在站与站之间流动。

批量做口播视频是一模一样的道理。你要做的不是"把一条视频做完"，而是把它拆成四个工位，让内容在工位之间流动：

| 工位 | 输入 | 输出 | 常用工具 |
|---|---|---|---|
| 1. 文案 | 主题/选题表 | 逐条口播稿 | 大模型 + 提示词模板 |
| 2. 配音 | 文本 | 音频 wav | CosyVoice / GPT-SoVITS |
| 3. 口型 | 音频 + 形象视频 | 无字幕成片 | MuseTalk / LatentSync |
| 4. 封装 | 成片 | 带字幕成品 | FFmpeg + Whisper |

关键在于：**每个工位的输出，必须是下一个工位能直接吃进去的格式**。

这句话听起来是废话。但我第一次跑批的时候，就死在这儿了。

## 为什么重要：省的不是时间，是切换成本

很多人以为批量的价值是"跑得快"。不对。

单条视频渲染2分钟，跑100条也要200分钟，这个时间省不掉。真正省下来的是**你的注意力**。

手工模式下，你每条要做13次操作：打开文档、复制文本、切到配音工具、粘贴、点生成、等、下载、改名、切到口型工具、上传、等、下载、加字幕。每次切换软件，大脑要重新载入一次上下文。这才是最贵的成本。

流水线模式下，你只做两件事：填一张选题表，然后回来收货。

我自己测过：同样50条视频，手工模式我做了两天半，中间还烦躁到想砸键盘；改成脚本跑批之后，我准备素材花了1小时，机器跑了3小时，我去健身房了。

差别不在速度。在于一个消耗人，一个不消耗人。

## 如何上手：从一张CSV表开始

### 第一步：把选题变成结构化数据

流水线的起点不是脚本，是**一张表**。

新建一个 `topics.csv`：

```
id,title,script,voice,avatar
001,什么是RAG,"RAG不是让AI变聪明，是让它学会翻书...",female_01,avatar_a
002,提示词三要素,"很多人写提示词像许愿...",female_01,avatar_a
003,Agent到底是什么,"给AI配个项目经理...",male_02,avatar_b
```

为什么用CSV不用文档？因为脚本能直接读。你在Excel里排好100行，剩下的交给循环。

### 第二步：搭好目录结构

乱是批量的最大敌人。我的目录长这样：

```
project/
├── topics.csv
├── avatars/          # 形象素材视频
├── output/
│   ├── audio/        # 第2站产物
│   ├── raw/          # 第3站产物
│   └── final/        # 第4站成品
├── logs/
└── run.sh
```

**一条铁律：所有文件名用CSV里的id开头。** `001_audio.wav`、`001_raw.mp4`、`001_final.mp4`。

这条规则救过我一次。有次跑到第60条崩了，因为文件名统一，我改了三个字符就从第61条续跑，没重来。

### 第三步：串起来的批处理脚本

核心逻辑就三层：读表 → 循环 → 每行走四站。

```bash
#!/bin/bash
while IFS=, read -r id title script voice avatar; do
  [ "$id" = "id" ] && continue
  echo "[$(date +%H:%M:%S)] 开始处理 $id - $title"

  # 站2：文本转语音
  python tts_cli.py --text "$script" --voice "$voice" \
    --out "output/audio/${id}_audio.wav" || { echo "$id TTS失败" >> logs/err.log; continue; }

  # 站3：口型驱动
  python inference.py --video "avatars/${avatar}.mp4" \
    --audio "output/audio/${id}_audio.wav" \
    --output "output/raw/${id}_raw.mp4" || { echo "$id 口型失败" >> logs/err.log; continue; }

  # 站4：字幕烧录
  whisper "output/audio/${id}_audio.wav" --model small --output_format srt \
    --output_dir output/audio/
  ffmpeg -y -i "output/raw/${id}_raw.mp4" \
    -vf "subtitles=output/audio/${id}_audio.srt:force_style='FontSize=18'" \
    "output/final/${id}_final.mp4"

  echo "[$(date +%H:%M:%S)] 完成 $id"
done < topics.csv
```

注意那两个 `|| { ... continue; }`。这是整个脚本里最重要的十个字符——**一条失败，跳过它，别拖垮整批**。

### 第四步：先跑3条，再跑100条

千万别一上来就 `done < topics.csv` 跑全量。

把CSV复制一份，只留3行，先跑通。确认这三条从音频到成品全对，再放全量。

我踩过的坑是：直接跑了80条，跑完发现字幕字号在竖屏视频里小得看不清。80条全部重烧，两个半小时白搭。

## 常见误区

**误区一：并发越多越快。**
错。我一开始开了8个并发，显存直接爆，进程全挂，日志里一片红。口型驱动是显存杀手，4G显存基本只能串行跑。正确做法：先单条测峰值显存，再决定并发数，宁少勿多。

**误区二：所有条目用同一套语速参数。**
文案长度不一样，固定语速会导致有的片子话说完了人还在动嘴。正确做法：在CSV里加一列 `speed`，长文案调到1.05，短文案调到0.95，或者干脆按字数在脚本里算。

**误区三：形象素材只准备一条。**
100条视频用同一段循环底片，观众三条就看腻了。正确做法：准备3到5段不同姿态的底片（正面讲述、侧身、手势），在CSV的 `avatar` 列里轮换。

**误区四：不写日志。**
不写日志的批处理等于闭眼开车。跑到一半崩了，你根本不知道崩在哪条。至少要记：开始时间、结束时间、失败id。一行 `echo` 的事。

**误区五：跑完不抽检。**
批量最大的风险不是失败，是"成功地做错了"。100条全渲染完成，结果口型全漂——因为音频采样率不对。我的规矩是：每20条抽1条完整看完。

## 进阶方向

- **加个断点续跑**：脚本开头判断 `output/final/${id}_final.mp4` 是否存在，存在就跳过。跑第二遍只补失败的。
- **失败重试机制**：把失败id写进 `retry.csv`，跑完主批之后自动过一遍。
- **跑完发通知**：脚本末尾调一个webhook，推到微信或飞书，不用守着屏幕。
- **接到内容源**：CSV这一层可以换成从表格工具、笔记库甚至RSS拉取，选题和产出就打通了。
- **上云跑**：本地显存不够的话，租一台带显卡的云主机，把整个目录扔上去跑，跑完拉回来。

明天讲数字人直播——从"录好的视频"到"实时的人"，中间隔着什么。

## 聊聊

你现在做内容，哪个环节最耗时间？是写稿、配音、剪辑，还是最后那些改名字、传文件的琐碎活？

我猜很多人卡在第四类——那些看起来不重要、但每天要重复几十次的动作。评论区说说你最想让机器替你干的那件事，我挑几个高频的下期专门拆。
